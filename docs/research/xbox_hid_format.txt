Research notes: how macOS GameController matches and parses an Xbox controller, and
which DriverKit entitlements a driver like XPadMac needs. Gathered on macOS 27.2
(Apple silicon) from local binaries (kernelcache, XboxGamepad.dext,
XboxOneHIDServicePlugin, GameController.framework), IOHIDFamily source, Apple DTS
forum threads, xpadneo and SDL. Machine- and account-specific details removed.

##### research:signing (generic parts)
=== FEASIBILITY VERDICTS ===
A) CoreHID HIDVirtualDevice / IOHIDUserDevice with com.apple.developer.hid.virtual.device: NOT feasible now. It needs Account Holder approval (no development version; months of queue as of Sep 2026). Neither root nor SIP-on gets around it. Even if approved, the device is forced to Transport="Virtual", so GameController matching is uncertain.
B) Development-signed DriverKit dext (USB GIP host + AppleUserHIDDevice), SIP ON: FEASIBLE with no Apple approval. Needs: a paid team signed in to Xcode (or the portal), the Mac registered as a macOS device in that team (by its Provisioning UDID), the host app in /Applications, user approval.
C) Developer ID-distributed dext: feasible, but the Account Holder must request DriverKit + USB Transport (the vendor IDs, in decimal) + HID Device family first; expect weeks.

<key>com.apple.developer.driverkit</key><true/>
<key>com.apple.developer.driverkit.transport.usb</key>
<array><dict><key>idVendor</key><string>*</string></dict></array>
<key>com.apple.developer.driverkit.family.hid.device</key><true/>
<key>com.apple.security.app-sandbox</key><true/>
<!-- optional, dev-only, only if the app opens an IOUserClient on the dext: -->
<!-- <key>com.apple.developer.driverkit.allow-any-userclient-access</key><true/> -->
Do NOT include com.apple.developer.hid.virtual.device or com.apple.developer.driverkit.family.hid.virtual.device in the dext.

=== Dext entitlements, RELEASE / Developer ID (only after Apple's approval) ===
com.apple.developer.driverkit = true
com.apple.developer.driverkit.transport.usb = [ { idVendor = <each vendor ID, decimal>; idProductArray optional } ]
com.apple.developer.driverkit.family.hid.device = true
In the request, give the IDs in both hex and decimal (e.g. VID 0x0E6F = 3695).

##### research:xbox-hid-format
I traced the whole matching and parsing path for a virtual Xbox controller on macOS 27.2, from local binaries rather than guesses. The safest choice is VID 0x045E / PID 0x0B13 (Xbox Series X|S over Bluetooth LE) using the controller's real 283-byte unified Bluetooth LE HID descriptor, copied byte for byte (CRC-16/ARC 0x931D, matching xpadneo). Input report ID 1 is 17 bytes; rumble arrives as output report ID 3, 9 bytes.

The kernel side: AppleGCHIDUserEventDriver::probe was disassembled from the decompressed kernelcache. When the personality has GCIOMatchVirtual=true, a virtual HID device matches unless it has GCSyntheticDevice=true, GameControllerEligible=false, or PrimaryUsagePage 0x84. Personalities without that flag (all the wired ones) need Privileged=true, which only the Apple-internal entitlement com.apple.hid.manager.user-access-device grants.

The parser: GameController does not read the descriptor generically. Reports are parsed at fixed byte offsets by /System/Library/HIDPlugins/ServicePlugins/XboxOneHIDServicePlugin.plugin, which runs in hidd. Its matchService accepts the device only if VendorID is 0x45E, Transport is not "USB", and the PID is in {02EA, 02FD, 02E0, 0B20, 0B02, 0B05, 0B22, 0B0C, 0B21, 0B13, 0B23, 0B4F, 0B3C}. Its initWithService then checks four descriptor elements to set flags: Brake 2/C5 and Accelerator 2/C4 (both present selects the 'Android' layout), Consumer AC Back C/224 (absent means View is a bit in the button field), and Consumer Record C/B2 (present means Share exists). With the 0x0B13 descriptor all four flags come out right: Android layout, View in byte 15 bit 2, Share in byte 16 bit 0, Guide in byte 15 bit 4.

Transport: IOHIDUserDevice forces Transport to "Virtual" for any creator that is not privileged (IOHIDFamily source), and "Virtual" passes the plugin's not-"USB" check. GameController's _GCMicrosoftXboxControllerProfile treats 0x0B12, 0x0B13, 0x0B23 and 0x0B4F as Series X, which includes the Share button.

Apple's wired dext (XboxGamepad.dext) holds four descriptors, identified by their symbol names. Three are 55-byte vendor-defined GIP pass-through descriptors and one is a 212-byte Xbox 360 descriptor. They do not help here, because the wired personalities lack GCIOMatchVirtual and the wired plugin (XboxGamepadHIDServicePlugin) only accepts 02EA, 0B00, 0B12 and 028E.

The earlier grep of the dyld cache was wrong. The string GameControllerSupportedHIDDevice is in GameController.framework (subcache .32) and in the kernel (IOGameControllerFamily's IOGCDynamicDeviceProbe).

Not verified end to end: creating any IOHIDUserDevice still needs a provisioning profile carrying com.apple.developer.hid.virtual.device. That is a 'HID Virtual Device' capability request to Apple, and an Apple forum thread reports waits of months.
- high | AppleGCHIDUserEventDriver::probe logic (kernel, macOS 27.2): reads GCIOMatchVirtual (OSBoolean, from the personality), and from the HID device CFBundleIdentifier, IOUserClass, GCSyntheticDevice, HIDVirtualDevice, Privileged, GameControllerEligible, plus PrimaryUsagePage from the IOHIDInterface. It rejects if PrimaryUsagePage==0x84, if GameControllerEligible isFalse, or if GCSyntheticDevice==kOSBooleanTrue. If GCIOMatchVirtual isTrue it returns a match right away. Otherwise a dext-backed device (IOUserClass and CFBundleIdentifier set) must have a bundle ID starting with 'com.apple.', and a device with HIDVirtualDevice==true must have Privileged present and not kOSBooleanFalse.
- high | The personalities that accept virtual devices (GCIOMatchVirtual=true) are: 'Xbox Wireless Controller' 045E:[02E0,02FD,0B20]; 'Xbox Series X Wireless Controller' 045E:[0B13,0B23,0B4F]; 'Xbox Elite V2 Controller' 045E:[0B02,0B05,0B22,0B3C]; plus Switch Pro 057E:2009 and DualSense 054C:0CE6. The wired personalities (360 028E, One S wired 02EA, Elite V2 USB 0B00, Series X wired 0B12) and the Adaptive Controller (0B0C, 0B21) do not have the flag.
- high | For a creator that is not privileged, IOHIDUserDevice forces Transport to 'Virtual' and sets HIDVirtualDevice=true and Privileged=false. 'Privileged' is true only with com.apple.hid.manager.user-access-device. Putting IOUserClientClass, IOClass, IOProviderClass, IOKitDebug, IOServiceDEXTEntitlements or Privileged in the properties makes creation fail with kIOReturnBadArgument.
- high | Bluetooth Xbox reports are parsed at fixed byte offsets in user space by XboxOneHIDServicePlugin (principal class, bundle com.apple.GameController.HID.XboxOne). Its plist matches services with GameControllerCategory='xbox' and GameControllerSupport=true. +matchService: needs super's match (GameControllerIO base class, which checks for AppleGCHIDUserEventDriver), VendorID==0x45E, Transport not equal to @"USB", and ProductID in {0x2EA,0x2FD,0x2E0,0xB20,0xB02,0xB05,0xB22,0xB0C,0xB21,0xB13,0xB23,0xB4F,0xB3C}. 'Virtual' or a missing Transport passes.
- high | -[XboxOneHIDServicePlugin initWithService:] picks the layout from PID and descriptor elements. Type: 0xB02/0xB05/0xB22/0xB3C='elite'(1); 0xB0C/0xB21='adaptive'(2); 0xB13/0xB23/0xB4F='series x'(3); anything else 'standard'(0). Descriptor flags come from [device elementsMatching:] with four constant dictionaries: {UsagePage 2, Usage 0xC5} brake, {2, 0xC4} accelerator, {0x0C, 0x224} AC Back, {0x0C, 0xB2} Record. _isAndroidProfile = brake AND accelerator present. _viewInDigitalButtonsField = no AC Back element. _shareButtonPresent = a Record element exists.
- high | Input report ID 1, as parsed by Apple with the Android layout (descriptors 0x0B13 and 02FD Linux-mode). Each item below is byte index: meaning. [0]: 0x01. [1..2] LX, [3..4] LY, [5..6] RX, [7..8] RY: u16 LE 0..65535, centre 0x8000, 0 = left/up, scaled as v/65536-0.5. [9..10] LT and [11..12] RT: u16 LE 0..1023, divided by 1023. [13]: hat in the low nibble, 0 neutral, 1=N, 2=NE, 3=E, 4=SE, 5=S, 6=SW, 7=W, 8=NW. [14]: bit0 A, bit1 B, bit3 X, bit4 Y, bit6 LB, bit7 RB. [15]: bit2 View (only when the descriptor has no AC Back), bit3 Menu, bit4 Xbox/Guide, bit5 LS, bit6 RS. [16]: bit0 Share when Record is present and View is in the digital field; otherwise bit0 = View (AC Back, 1708 Linux-mode). Report 2: data[1] bit0 = Home (dispatchAlternateHome). Report 4: data[1] is a battery bitfield (Level b0-1, Type b2-3, Charge b4-5, PowerLevel b6-7). The handler does not check length, so send the full 17 bytes.
- medium | Windows layout (no Brake/Accelerator, as in the 1708 'Windows mode' 306-byte descriptor). Byte index: meaning. [14]: bit0 A, bit1 B, bit2 X, bit3 Y, bit4 LB, bit5 RB, bit6 View, bit7 Menu. [15]: bit0 LS, bit1 RS. Guide only via report 2. Avoid this layout.
- high | Apple sends rumble as an Output report: setReport length 9, reportID 3, type kIOHIDReportTypeOutput. Byte index: meaning. [0]: 0x03. [1]: 0x0F when haptics are active, 0xFF when stopping. [2]: Left Impulse (LT). [3]: Right Impulse (RT). [4]: Left Rumble (strong/low frequency). [5]: Right Rumble (weak/high frequency). Each magnitude is GCHapticMotor intensity x100, range 0..100. [6]: duration, 0x0A (10 x 10 ms) when active, 0 when stopping. [7]: delay 0. [8]: loop count 0. No rumble is sent for type 2 (Adaptive). The magnitudes have the same 0..100 scale as the GIP 0x09 payload, so they can be forwarded directly to a GIP pad.
- high | The Series X|S Bluetooth LE descriptor (0x0B13, also used by every non-Elite model on BLE firmware) is 283 bytes, CRC-16/ARC 0x931D. It has Report 1 Input (16 payload bytes, 17 with the ID) and Report 3 Output (8 bytes, 9 with the ID), and no battery report 4. The xpadneo parsed comment 'Logical Maximum (65534)' is wrong: 27 FF FF 00 00 decodes to 65535.
- medium | The Xbox One S 1708 Bluetooth Classic descriptor (PID 0x02FD, 'Linux mode', firmware 4.8 era) is 334 bytes. Report 1 Input is 16 bytes (17 with the ID), the same as the BLE layout except byte 16 bit0 is Consumer AC Back (View) instead of Record. Report 2 Input is Consumer AC Home (1 byte). Report 3 is the same rumble output. Report 4 is Generic Device Battery Strength (1 byte). Fed to Apple's plugin, this descriptor gives the Android layout, View at [16] bit0, and no Share.
- medium | GameController.framework's Xbox profile picks the physical input type from the PID only. 0xB12, 0xB13, 0xB23 and 0xB4F give type 3, 'Series X' (adds buttonShare). 0xB02 and 0xB05 give Elite (paddles). 0xB0C gives Adaptive. Everything else, including 02E0/02FD/0B20, gives standard Xbox One with no Share.
- high | XboxGamepad.dext descriptors, identified by symbol: 0x1C000 is Xbox360HIDGamepadDeviceDescriptor (212 bytes, the 360 wired layout: report without ID, 20 bytes; plus Output ID 0x31, 77 bytes). 0x1C0D4 is XboxOneSGamepadUSBHIDDeviceDescriptor (55 bytes). 0x1C10B is XboxSeriesXGamepadUSBHIDDeviceDescriptor (55). 0x1C142 is XboxEliteV2GamepadUSBHIDDeviceDescriptor (55). The 55-byte ones are vendor page 0xFF00 GIP pass-through: Output ID1 12 bytes, Output ID5 4 bytes, Input ID7 5 bytes (GIP virtual-key/guide), Input ID 0x20 of 17 bytes (One S, Elite V2) or 18 bytes (Series X, Share). The same data is in both slices (arm64e and arm64e.x1 at +0x2C000). XboxWirelessGamepad has no descriptor of its own. These are consumed by XboxGamepadHIDServicePlugin, which accepts only 045E:02EA/0B00/0B12/028E, so they are not usable for a virtual device without privilege.
- high | GameController creates its own virtual Xbox 360 devices (_GCSyntheticXbox360Controller). They carry a 188-byte 360 descriptor, Manufacturer 'Microsoft', Product 'GamePad-1', VendorID, ProductID, VersionNumber, and are tagged GCSyntheticDevice, which is the property the kernel probe uses to keep them away from GameController. This confirms a minimal property set works for Apple's own virtual Xbox device.
- high | The earlier claim that 'GameControllerSupportedHIDDevice' is absent from the dyld cache was wrong. Checked against a known string (GCControllerDidConnectNotification, found in .15/.21/.32/.34), GameControllerSupportedHIDDevice is at subcache .32 offset 0x78e995c, inside GameController (next to 'GCController.supportsHIDDevice' and 'IOGCDynamicDeviceProbe'). It is also in the kernel at IOGameControllerFamily, whose 'Dynamic IOHIDDevice Probe' (IOGCDynamicDeviceProbe) matches every GD 1/4 and 1/5 IOHIDDevice and has a user client.
- medium | The virtual-device route still depends on Apple granting com.apple.developer.hid.virtual.device in a provisioning profile, via the 'HID Virtual Device' capability request. An Apple DTS engineer said GameController matches 'specific (undocumented) hardware details' and was not certain a CoreHID virtual gamepad would be recognized. One reported request had been pending about 2.5 months.

=== Input report 1 (17 bytes; layout as Apple's XboxOneHIDServicePlugin parses it) ===
#pragma pack(push,1)
typedef struct {
  uint8_t  report_id;            /* 0x01 */
  uint16_t lx, ly, rx, ry;       /* LE, 0..65535, centre 0x8000, 0 = left / up */
